В [прошлой статье](/p/ai-tools-2026-aider) мы успешно настроили базовый изолированный пайплайн на связке **uv + Aider + Ollama** в Ubuntu и научились собирать одиночные `.patch` файлы в неинтерактивном режиме с помощью флага `--message`. 

Однако при переходе от простейших скриптов к промышленной автоматизации — например, когда нужно одной командой сгенерировать синхронную документацию сразу на двух языках (русском и английском) — разработчики натыкаются на неочевидные архитектурные барьеры: циклическую ошибку `404 Not Found`, лавинообразное раздувание контекста и затирание Git-диффов.

Разбираем продвинутую инженерию автоматизации ИИ-агентов на примере генерации мультиязычной документации для реактивного декоратора `withStaleWhileRevalidate`.

## 1. Разделение Глобального Каркаса и Локальной Задачи
Чтобы ИИ-агент работал стабильно, его мышление необходимо разделить на два независимых слоя: **Глобальные инструкции (Стиль и Структура)** и **Локальная задача (Контекст и Данные)**. Для этого мы полностью изолируем среду документирования с помощью файлов `.aider.instructions.md` и специализированного `.env.doc`.

### Схема взаимодействия компонентов конвейера
```
[ .env.doc ] ───────> ( Динамические переменные: Таргет сущности / Пути к файлам )
                                    │
                                    ▼
[ .aider.instructions.md ] ─> [ ИИ-Агент Aider ] <─── [ Исходный код, Типы и Тесты ]
( Глобальный каркас стиля )         │                   ( src/core/types.ts, .test.ts )
                                    ▼
                           ┌─────────────────┐
                           │  Последователь  │
                           │  Сплит-Сессий   │
                           └────────┬────────┘
                                    │
                   ┌────────────────┴────────────────┐
                   ▼                                 ▼
            [ Сессия 1: RU ]                  [ Сессия 2: EN ]
        (docs/decorators/.md)            (docs/en/decorators/.md)
                   │                                 │
                   └────────────────┬────────────────┘
                                    ▼
                      [ Атомарный Git-дифф сборки ] ──> [ docs_multilang_update.patch ]
```

### Реализация Глобального Каркаса (`.aider.instructions.md`)
Этот файл содержит неизменяемые правила игры, написанные на английском языке (наиболее приоритетный язык для системных промптов локальных моделей). Он заставляет ИИ строго следовать структуре исходных примеров документации (`withCache`) [source: 0.1.1], запрещает галлюцинации и фиксирует правила перевода технических терминов.

```markdown
# Role & Objective
You are an expert technical writer specializing in reactive architecture. Your job is to create documentation pages for decorators or methods in the Reactive Engine library. Maintain strict layout constraints and 100% technical accuracy based on source code and tests.

# Language Strategy
- You will be told which language to use (**Russian** or **English**) in the task command.
- Generate all headers, explanations, and code comments strictly in the target language.
- Keep technical signatures, types, and API methods (.push, ResourceState) in English.

# Output Document Structure Constraint
Every markdown page MUST follow this exact structure:
# {Entity Name}
{High-level summary}.
## Синтаксис / Syntax
\`\`\`typescript
// Precise type signature
\`\`\`
## Параметры / Parameters
- **paramName** (`Type`): Description.
## Возвращаемое значение / Return Value
- List all public properties, methods, and flags.
## Примеры / Examples
1. Basic usage scenario.
2. Advanced scenario (error handling, mutations from tests).
## Дополнительная информация / Additional Information
```

### Изоляция Локальной Задачи (`.env.doc`)
Для запуска пайплайна документации создается обособленный конфигурационный файл. В нем мы полностью отказываемся от OpenAI-совместимого эндпоинта `/v1`, так как библиотека `liteLLM` в составе Aider пытается выполнить служебный запрос `api/show` на некорректный адрес `.../v1/api/show`, вызывая краш 404. Мы используем **нативный контур Ollama**:

```env
# --- Нативный эндпоинт Ollama (Без /v1 для обхода бага 404 в liteLLM) ---
OLLAMA_API_BASE="http://127.0.0.1:11434"
AIDER_MODEL="ollama/qwen2.5-coder:14b"

# --- Архитектурные флаги ИИ-агента ---
AIDER_CHAT_MODE="code"
AIDER_MAP_TOKENS=0
AIDER_DISABLE_AUTO_COMMITS="true"
AIDER_OUTPUT_PATCH="docs_multilang_update.patch"

# --- Имя целевой сущности и точечный контекст ---
DOC_TARGET_ENTITY="withStaleWhileRevalidate"
AIDER_FILES="src/core/types.ts,src/decorators/withStaleWhileRevalidate/withStaleWhileRevalidate.ts,src/decorators/withStaleWhileRevalidate/withStaleWhileRevalidate.test.ts,docs/decorators/withStaleWhileRevalidate.md,docs/en/decorators/withStaleWhileRevalidate.md"
```

## 2. Выбор LLM в Зависимости от Вычислительных Ресурсов

<CollapsibleBox
isEnabledForNavigation='1'
header="KV-кэш (Key-Value Cache) — это..."
text="Специализированная технология оптимизации, которая используется в больших языковых моделях (LLM) для ускорения генерации текста и экономии вычислительных ресурсов процессора (CPU или GPU).
&nbsp;
Если говорить простыми словами, **KV-кэш — это «кратковременная память» нейросети о тех токенах (словах), которые она уже прочитала или сгенерировала в рамках текущего диалога.**
&nbsp;
**Проблема: Почему нейросети «дорого» генерировать текст?**
&nbsp;
Языковые модели работают по принципу авторегрессии — они предсказывают текст **строго по одному слову (токену) за раз.**
Когда вы отправляете в Aider промпт из 5000 токенов, модель:
&nbsp;
**1.** Вычисляет математические связи (внимание/attention) между всеми этими 5000 токенами.
**2.** Генерирует **1-е** новое слово.
**3.** Чтобы сгенерировать **2-е слово,** ей нужно взять исходные 5000 токенов + 1-е сгенерированное слово и **заново** пересчитать все связи с самого начала.
&nbsp;
Без оптимизации процессор Ryzen AI 9 на каждом новом слове совершал бы квадратичный объем холостых вычислений, выполняя одну и ту же работу по кругу. Скорость генерации (TPS) падала бы с каждым следующим словом.
&nbsp;
**Решение: Как работает KV-кэш?**
&nbsp;
В процессе расчета механизма внимания (Self-Attention) для каждого токена вычисляются три вектора: **Q**uery (Запрос), **K**ey (Ключ) и **V**alue (Значение).
&nbsp;
Смысл **KV-кэша** заключается в том, что модель вычисляет векторы Ключей (**K**) и Значений (**V**) для контекста **всего один раз** и сохраняет их в оперативной памяти.
&nbsp;
• Когда модель генерирует следующее слово, она берет его вектор **Q,** а векторы **K** и **V** для всех предыдущих 5000 слов **просто достает из кэша в памяти,** не пересчитывая их на CPU.
• Скорость генерации остается стабильной и высокой от первого до последнего слова.
&nbsp;
**Обратная сторона: Почему из-за KV-кэша модель «глупеет»?**
&nbsp;
Хотя KV-кэш экономит миллиарды математических операций процессора, он имеет жесткие ограничения:
&nbsp;
**1. Лавинообразное потребление памяти:** KV-кэш «живет» в RAM/VRAM. Чем длиннее история вашего диалога (context window), тем больше места занимает этот кэш. Если вы загрузили в Aider массивные файлы `types.ts` и тесты, а потом долго общаетесь в одной сессии, KV-кэш может раздуться до десятков гигабайт, вытесняя саму модель в медленный файл подкачки (swap).
&nbsp;
**2. Размытие матрицы внимания:** Когда KV-кэш переполнен, локальной модели (например, Qwen 14B) становится математически сложнее сфокусировать вектор Query (**Q**) на нужных Ключах (**K**). Вектора «средней части» диалога начинают сливаться в белый шум. Модель физически теряет способность удерживать фокус на системных инструкциях `.aider.instructions.md`, которые лежат в самом начале этого гигантского массива данных.
&nbsp;
**Именно поэтому наши сплит-сессии так эффективны:** уничтожая историю чата между шагами RU и EN, мы полностью стираем раздутый KV-кэш истории. Модель каждый раз начинает работу с «чистой, легкой головой», видя только жесткие файлы контекста и свежие инструкции."
/>

Локальный запуск на процессоре **AMD Ryzen AI 9 HX 470** с графикой Radeon 890M означает, что модель выполняется на CPU с задействованием системной оперативной памяти, используя мощное аппаратное ускорение инструкций **AVX-512**.

header="AVX-512 (Advanced Vector Extensions 512) — это..."
text="Специализированный набор векторных (SIMD) инструкций процессора, разработанный для экстремального ускорения сложных математических расчетов.
&nbsp;
Если говорить простыми словами, обычный процессор обрабатывает данные последовательно — «одна команда для одного числа». Процессор с поддержкой AVX-512 работает как конвейер суперкомпьютера: он способен применить одну команду (например, умножение или сложение векторов) сразу к огромному массиву данных за один единственный такт. Цифра **512** указывает на размер регистров процессора в битах — внутри них можно одновременно обрабатывать, например, 16 чисел с плавающей запятой высокой точности (float32) или 64 восьмибитных целых числа (int8).
&nbsp;
Когда Ollama запускает модель на процессоре **AMD Ryzen AI 9:**
&nbsp;
**1. Многократное ускорение (SIMD):** Вместо того чтобы гонять ядра процессора по одиночным ячейкам памяти, инструкции AVX-512 позволяют за один такт ядра перемножать целые строки и столбцы нейросетевых матриц.
&nbsp;
**2. Аппаратная квантизация:** Локальные модели для экономии памяти сжимают (квантуют) до 8 или 4 бит (форматы `Q8_0`, `Q4_K_M`). Архитектура AVX-512 в процессорах AMD последнего поколения содержит специализированные микро-команды (например, AVX-512 VNNI), которые «на лету» на аппаратном уровне щелкают эти сжатые целые числа, выдавая огромную скорость генерации (TPS) даже без использования дорогой видеокарты Nvidia.
&nbsp;
По сути, благодаря AVX-512 **Ryzen AI 9** превращается в мощный локальный ИИ-ускоритель, позволяя комфортно и быстро запускать тяжелые модели уровня 14B–32B прямо в оперативной памяти компьютера."

При текущей конфигурации памяти и в перспективе апгрейда (две плашки по 64 ГБ RAM, суммарно 128 ГБ), а также при альтернативном сценарии с дискретной видеокартой (VRAM), выбор моделей распределяется следующим образом:

| Вычислительный ресурс | Рекомендуемая LLM | Токенов в сек. (TPS) | Архитектурное поведение и качество |
| :--- | :--- | :--- | :--- |
| **Текущий CPU**<br />(Ryzen AI 9 + AVX-512 + Shared RAM) | `qwen2.5-coder:14b` | **15 – 25** | **Оптимальный баланс.** Быстрый отклик. Четко держит структуру markdown, но может точечно нарушить языковое табу (например, перевести `.push` на русский). |
| **Текущий CPU**<br />(Ryzen AI 9 + AVX-512 + Shared RAM) | `qwen2.5-coder:32b` | **4 – 8** | **Тяжело для CPU.** Высочайшее качество и строгое следование промпту, но TDD-цикл может казаться зависшим из-за низкой скорости. |
| **Апгрейд до 128 ГБ RAM**<br />(2x64 ГБ SODIMM DDR5 на CPU) | `qwen2.5-coder:32b`<br />(или `qwen3-coder:30b`) | **8 – 14** | **Целевой режим.** Огромный объем RAM нивелирует раздувание KV-кэша на сложных многофайловых рефакторингах. Модель полностью загружается в память без риска своппинга. |
| **Альтернатива на VRAM**<br />(Дискретная GPU Nvidia с 16 ГБ VRAM) | `qwen2.5-coder:14b`<br />(полный инференс на GPU) | **40 – 60** | **Мгновенный TDD.** Идеально для частых итеративных правок кода. Ограничение — 14B предел по объему памяти карты. |
| **Альтернатива на VRAM**<br />(Дискретная GPU Nvidia с 24 ГБ VRAM, e.g., RTX 3090/4090) | `qwen2.5-coder:32b`<br />(квантование Q4_K_M / Q8_0) | **35 – 50** | **Ультимативный индустриальный стек.** Максимальное качество кодинга, мгновенный инференс, полное следование графу Tree-sitter. |

## 3. Разделение Сессий: Борьба с Раздуванием Контекста

Почему автоматический Bash-скрипт `ai_ollama_aider_generate_doc.sh` запускает Aider дважды (сначала для RU, затем для EN), а не просит сгенерировать оба файла в рамках одной длинной интерактивной сессии? 

Это обусловлено тремя критическими факторами ИИ-инженерии:

### 1. Математика KV-Кэша и Эффект «Потери в Середине» (Lost in the Middle)
Когда Aider инициализирует сессию, он строит карту репозитория (Repo Map) через Tree-sitter и подгружает типы `types.ts`, код декоратора и тесты. Это формирует тяжелый стартовый контекст. 
* Если заставить модель писать **сначала русский текст, а затем английский в одном диалоге**, контекстное окно раздувается лавинообразно. 
* К моменту генерации английской версии KV-кэш переполняется, локальная модель начинает «забывать» инструкции из начала диалога (из файла `.aider.instructions.md`) и начинает путать структуры заголовков или мешать языки.
* **Выигрыш сплит-сессий:** Каждая сессия стартует с чистым контекстом истории диалога. Модель помнит исходный код, но сфокусирована только на одной задаче генерации.

### 2. Исключение Лингвистической Интерференции
У локальных моделей среднего размера (14B–32B) при генерации больших объемов текста на разных языках в рамках одного контекстного окна возникает «перетекание» токенов. Модель может начать комментировать английский код русскими словами или использовать кальку с русского синтаксиса в секциях английской документации. Разделение сессий гарантирует ментальную изоляцию: модель находится либо в жестком контуре `[LANGUAGE: RUSSIAN]`, либо `[LANGUAGE: ENGLISH]`.

### 3. Контроль Сбоев и Сохранение Git-Диффа
Если при генерации второго (английского) файла локальная Ollama выдаст ошибку или сбойнет по таймауту, первая (русская) версия уже будет физически записана на диск. Накопительный режим работы скрипта (когда `git checkout -- .` выполняется **строго до начала всех сессий**, а не между ними) позволяет Git атомарно отследить изменения в обоих файлах и упаковать их в единый патч-артефакт `docs_multilang_update.patch` без потери данных.

### Разбор математики контекста на реальном примере

Эффективность разделения сессий наглядно подтверждается метриками токенов. В изолированном конвейере на первом шаге (RU-локализация) локальная модель получает **4.9k токенов** входящего контекста (архитектура, исходный код, типы и системные правила) и генерирует **1.2k токенов** ответа. На втором шаге (EN-локализация) Aider запускается с чистой историей диалога: на вход подается **6.0k токенов** (исходный код плюс уже созданный на диске русский файл для синхронизации структуры), а модель выдает **977 токенов** чистого английского текста. Если бы мы объединили эти шаги в одну общую интерактивную сессию, входящий контекст второго шага раздулся бы до **7.5k+ токенов** за счет накопленной истории чата. Для локальной модели это критический порог: перегрузка KV-кэша приводит к эффекту «потери в середине» (Lost in the Middle), когда ИИ начинает игнорировать системные инструкции из начала диалога, путает структуру markdown-разметки и допускает лингвистическое перетекание (интерференцию) русского текста в английский код.

## Итог: Сравнительный анализ подходов управления контекстом

| Критерий сравнения | Накопительные сплит-сессии (Выбранный подход) | Единая долгоживущая сессия (Интерактивный чат) |
| :--- | :--- | :--- |
| **Объем входящего контекста (Sent)** | **Минимальный (4.9k / 6.0k)**. Модель видит только файлы на диске, история диалога пуста. | **Лавинообразный (7.5k+)**. Входной контекст постоянно растет за счет истории предыдущих ответов. |
| **Качество следования промпту** | **Идеальное**. Системные правила `.aider.instructions.md` имеют максимальный приоритет в окне внимания модели. | **Деградирует**. Инструкции «вымываются» из памяти модели под давлением сгенерированных портянок текста. |
| **Лингвистическая изоляция** | **Полная**. Модель находится в жестких рамках одного целевого языка на каждую сессию. | **Нарушена**. Высокий риск смешивания языков и калькирования фраз из-за присутствия старого текста в чате. |
| **Нагрузка на CPU (Ryzen AI 9)** | **Низкая**. Меньше токенов в памяти — быстрее пересчет матрицы внимания и выше скорость генерации (TPS). | **Высокая**. Процессор тратит критически много времени на обработку тяжелого и грязного KV-кэша. |
| **Устойчивость к сбоям** | **Высокая**. Падение второй сессии не уничтожает результаты первой; Git атомарно соберет частичный патч. | **Нулевая**. Любая ошибка локальной Ollama в конце долгого диалога приводит к потере всего сгенерированного текста. |
