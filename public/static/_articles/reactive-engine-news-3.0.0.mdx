## Архитектурные изменения

### В чем новизна мажорного релиза?

Переход с ветки **v2.7.2** на **v3.0.0** — это не просто оптимизация отдельных методов, а полная смена фундаментальной модели хранения и обхода реактивного графа. Если архитектура 2.x строилась вокруг стандартных коллекций JavaScript (`Set` и `Map`), то в 3.0.0 ядро переведено на **двунаправленные интрузивные списки (`NodeLink`),** пулинг памяти и курсорный трекинг зависимостей — паттерны, которые используют самые быстрые современные движки (`alien-signals`, `@vue/reactivity` 3.5+).

<CollapsibleBox
isEnabledForNavigation='1'
header="Двунаправленные интрузивные связи (doubly-linked intrusive lists) — это..."
text="Способ организации связей в графе, при котором ссылки на соседние элементы хранятся прямо внутри самих объектов рёбер (`NodeLink`), без создания внешних контейнеров вроде `Set`, `Map` или массивов.
&nbsp;
В реактивном движке v3.0.0 этот подход состоит из двух частей:
&nbsp;
**Интрузивность (встроенность):** Вместо того чтобы хранить ссылки в отдельной коллекции (где память выделяется под сам объект Set и его внутренние бакеты), каждый объект связи NodeLink сам содержит указатели next и prev. Объект «встроен» в структуру списка напрямую.
&nbsp;
**1. Двунаправленность (ортогональная сетка):** Каждый объект `NodeLink` одновременно состоит сразу в двух независимых двусвязных списках:
&nbsp;
**2. По горизонтали (`nextSubscriber` / `prevSubscriber`):** связывает все эффекты и вычисления, подписанные на один и тот же источник.
&nbsp;
**3. По вертикали (`nextDependency` / `prevDependency`):** связывает все источники, от которых зависит один и тот же потребитель.
&nbsp;
**Зачем это нужно**
&nbsp;
👉 Удаление за O(1) без поиска: Чтобы отписать узел, движку не нужно искать его в Set или вычислять хэш — достаточно перекинуть ссылки `prev.next = next` и `next.prev = prev` на соседних рёбрах.
&nbsp;
👉 Минимум мусора для GC: При разрыве связи объект `NodeLink` не удаляется, а обнуляется и возвращается в пул (`LinkPool`) для мгновенного переиспользования."
/>

Ниже приведена ASCII-схема, показывающая, как два сигнала (**S1, S2**) и два потребителя (**C1, E1**) связываются в единую ортогональную сетку через объекты `NodeLink` без использования `Set` и `Map`.
```
                        СТОЛБЦЫ: Потребители (Consumers)

                    [ C1 (Computed) ]                      [ E1 (Effect) ]
                            │                                      │
                    dependenciesHead                       dependenciesHead
                            ▼                                      ▼
  СТРОКИ:          ┌─────────────────┐   nextSubscriber   ┌─────────────────┐
  Источники        │   NodeLink #1   │ ─────────────────► │   NodeLink #2   │
  (Sources)        │                 │                    │                 │
                   │ source: S1      │ ◄───────────────── │ source: S1      │
  [ S1 ] ─────────►│ target: C1      │   prevSubscriber   │ target: E1      │
  subscribersHead  └─────┬─────▲─────┘                    └─────────────────┘
                         │     │
          nextDependency │     │ prevDependency
                         ▼     │
                   ┌─────┴─────┴─────┐
                   │   NodeLink #3   │
                   │                 │
                   │ source: S2      │
  [ S2 ] ─────────►│ target: C1      │
  subscribersHead  └─────────────────┘
```

**Как читать эту матрицу:**

**`nextSubscriber` и `prevSubscriber` (горизонтальная ось):** Связывают подписчиков одного источника (**S1**). Указатель `nextSubscriber` ведёт от **NodeLink #1** к **NodeLink #2,** а `prevSubscriber` возвращает обратно.

_Это список всех, кто подписан на конкретный сигнал. Чтобы уведомить подписчиков **S1**, движок берёт первый узел строки (**NodeLink #1**) и просто идёт вправо до **NodeLink #2**._

**`nextDependency` и `prevDependency` (вертикальная ось):** Связывают зависимости одного потребителя (**C1**). Указатель `nextDependency` ведёт вниз от **NodeLink #1** к **NodeLink #3,** а prevDependency указывает обратно вверх.

_Это список всех зависимостей конкретного потребителя. Чтобы пересчитать **C1**, движок берёт верхний узел столбца (**NodeLink #1**) и шагает вниз до **NodeLink #3**._

**Почему нет **Set** и **Map**:** Ни у **S1**, ни у **C1** нет массивов или хэш-таблиц.

**Почему нет полей `subscribers` и `dependencies` на узлах:** Сами узлы **S1,** **S2,** **C1** и **E1** хранят только входную точку списка (`subscribersHead` или `dependenciesHead`). Все связи между соседями лежат внутри самих объектов `NodeLink`.

_Каждый узел хранит только одну ссылку на начало своей строки или столбца, а все остальные связи прошиты внутри самих ячеек `NodeLink`_

> [!info] **Как движок читает эту сетку за O(1)?**
>
> **Обход по горизонтали (`nextSubscriber` / `prevSubscriber`):** Когда меняется сигнал **S1,** движок берёт `S1.subscribersHead` (**NodeLink #1**) и просто шагает вправо по указателю `nextSubscriber` к **NodeLink #2.** Так он за один проход уведомляет всех подписчиков **S1** (**C1** и **E1**).
>
> **Обход по вертикали (`nextDependency` / `prevDependency`):** Когда пересчитывается **C1,** курсор `depsCursor` встаёт на `C1.dependenciesHead` (**NodeLink #1**) и шагает вниз по `nextDependency` к **NodeLink #3.** Так **C1** сверяет все свои зависимости (**S1** и **S2**) без пересоздания объектов.
>
> **Мгновенное удаление из обеих осей:** Если **C1** перестаёт зависеть от **S1** (переключилась ветка `if`), **NodeLink #1** вырезается из горизонтального списка **S1** и вертикального списка **C1** простой переброской соседних указателей, а сам объект возвращается в `LinkPool`.

Ниже разобраны четыре ключевых архитектурных изменения, которые позволили кратно сократить накладные расходы и вывести движок в верхний эшелон мировых бенчмарков (`js-reactivity-benchmark`).

#### 1. Отказ от `Set` и `Map` в пользу двунаправленных рёбер (`NodeLink`)
- Как было в v2.7.2: Каждый узел графа (`Signal`, `Computed`, `Effect`) хранил свои связи в хэш-таблицах (`subscribers: Set`, `dependencies: Set`, `depVersions: Map`). При любом динамическом переключении веток движок тратил такты процессора на вычисление хэшей, реаллокацию бакетов и создание итераторов при обходе подписчиков.
- Как стало в v3.0.0: Каждая связь между источником и потребителем представлена плоским мономорфным объектом `NodeLink`, который одновременно входит в два двунаправленных связных списка:
	- список подписчиков источника (`nextSubscriber` / `prevSubscriber`);
	- список зависимостей потребителя (`nextDependency` / `prevDependency`).
- Что это дало: Обход графа вверх и вниз превратился в линейное чтение указателей в памяти. Нагрузка на кэш процессора снизилась, а V8 перестал деоптимизировать горячие циклы из-за полиморфизма коллекций.

#### 2. Пулинг объектов (`LinkPool`) и защита от сборки мусора (GC-Free)
- Как было в v2.7.2: При каждом пересчёте `computed` или перезапуске `effect` старые коллекции очищались, а новые ссылки выделялись заново. В динамических сценариях (когда зависимости меняются на каждом тике) это создавало постоянное давление на сборщик мусора (GC).
- Как стало в v3.0.0: Внедрён статический пул `LinkPool`. Когда ребро графа разрывается, объект `NodeLink` не выбрасывается в кучу, а обнуляется и возвращается в пул для мгновенного повторного использования.
- Что это дало: В длительных стресс-тестах (`dynamic` и `kairo`) аллокации новых рёбер в горячем цикле сведены практически к нулю.

#### 3. Курсорное переиспользование связей за O(1)
- Как было в v2.7.2 (и ранней 3.0.0-alpha.0): Перед каждым пересчётом узла все его старые зависимости разрывались (`unlinkDependencies`), а затем собирались заново. Если узел зависел от 1000 сигналов, а менялся только один, движок всё равно пересоздавал 1000 связей.
- Как стало в v3.0.0: Перед запуском функции вычисления курсор (`depsCursor`) ставится в начало существующего списка зависимостей. Если на i-м шаге код читает тот же сигнал, что и в прошлый раз, курсор просто сдвигается вперёд за **O(1)** — без поиска, без удаления и без обращения к пулу. Только если ветка исполнения изменилась и в конце остался «хвост» неиспользованных связей, они отрезаются и уходят в `LinkPool`.
- Что это дало: В тесте `updateComputations1000to1` время выполнения упало с 1070 мс до 18.5 мс (ускорение в 57 раз).

#### 4. Двухуровневая верификация «грязи» и локальные версии
- Как было в v2.7.2: Версии зависимостей хранились в отдельных Map, а при откатах транзакций (Net-Zero мутации внутри `batch`) требовались дополнительные проходы для сверки состояний.
- Как стало в v3.0.0: Каждое ребро `NodeLink` само хранит снимок версии источника (`link.version`) в момент последнего чтения. Волна инвалидации делится на два состояния: **DIRTY (источник точно изменился)** и **CHECK (нужно лениво проверить цепочку вверх).** Если промежуточный `computed` пересчитался, но вернул прежнее значение (`Object.is`), его версия не растёт, и каскад обновлений мгновенно гасится.

### Разбор проваленных тестов #212 и #213

В наборе тестов на семантику графа [reactive-framework-test-suite](https://github.com/johnsoncodehk/reactive-framework-test-suite) `reactive-engine` v3.0.0 набрал **98.8% (159 из 161)**, показав паритет с `@vue/reactivity` 3.5.45. Единственные два не пройденных кейса (**#212** и **#213**) относятся к разделу **Inner Write** (запись в корневой сигнал прямо из тела эффекта, который сам же от него зависит). Примечательно, что ровно на этих же двух тестах спотыкаются и официальный полифил **TC39 Signals (`signal-polyfill`)**, и **`@solidjs/signals`**.

#### Что именно проверяют эти тесты?

Оба теста моделируют паттерн «самокорректирующегося эффекта» (feedback loop) через промежуточное вычисляемое значение:

<CollapsibleBox
isEnabledForNavigation='0'
header="Feedback Loop — это..."
text="Цикл обратной связи — фундаментальный механизм в системах управления и самообучающихся системах, при котором выходные данные системы используются для корректировки её поведения. Он обеспечивает адаптацию и устойчивость, позволяя системе поддерживать желаемое состояние даже при внешних возмущениях. В машинном обучении и искусственном интеллекте цикл обратной связи играет ключевую роль в обучении с подкреплением, управлении роботами и построении адаптивных алгоритмов."
/>

**Вариант 1 описания (в точности как в карточках тестов #212 и #213 сьюта):**

```text
S(s) ─→ C(c) ←─ E(eff) ═→ S(s) [writes 0 when c > 0]
```

**Вариант 2 (более развернутый):**

```
Legend:
  S        signal (source)
  C        computed
  E / eff  effect
  ─→       dependency edge (downstream reads upstream)
  ═→       inner write (effect writes back to upstream signal)

  ┌─────────────────── inner write (s = 0) ───────────────────┐
  │                                                           ║
  ▼                                                           ║
S(s) ─────────→ C(c) [s * 2] ─────────→ E(eff) [if c > 0] ════╝
```

1. **Тест #213 (`inner write during initial effect execution doesn't block future propagation`):**
   * Корневой сигнал **s** изначально имеет положительное значение (например, `1`).
   * Создаётся **computed** `c`, зависящий от `s`, и **effect** `eff`, который читает `c`.
   * Прямо во время **первого (синхронного) запуска** при инициализации `eff` видит, что `c > 0`, и сразу сбрасывает корневой сигнал `s` обратно в значение `0`.
   * *Проблема:* Если движок во время инициализации эффекта блокирует повторную постановку этого же эффекта в очередь (защищаясь от бесконечной рекурсии), флаги «грязи» на промежуточном узле `c` могут остаться в неконсистентном состоянии. В результате **следующие** внешние записи в `s` перестают пробуждать `eff`.

2. **Тест #212 (`inner write through computed doesn't block future propagation`):**
   * Сценарий идентичен #213, но изначально `s` равен `0` (при инициализации эффект ничего не перезаписывает).
   * Затем происходит внешняя запись `s = 1`, которая через `c` запускает `eff`. Эффект срабатывает и внутри себя сбрасывает `s = 0`.
   * *Проблема:* Волна инвалидации от внутренней записи `s = 0` накладывается на ещё не завершённый цикл обработки первого эффекта. Если **computed** `c` при этом не сбросит свой статус актуальности корректно, цепочка `s → c → eff` «глохнет» и перестаёт реагировать на дальнейшие изменения `s`.

#### Повлияет ли это на реальный код?

В **99% практических сценариев — нет**, и вот почему:

1. **Антипаттерн в проектировании:** Мутировать корневой источник данных прямо внутри эффекта, который от него же зависит (создавая синхронный цикл обратной связи), считается плохой практикой в любой реактивной системе. Обычно такие задачи решаются либо на этапе записи (в экшене/методе), либо через `computed` с приведением границ (clamping).
2. **Отраслевая норма:** Тот факт, что точно так же ведут себя `@solidjs/signals` и эталонный `signal-polyfill` от комитета TC39, подтверждает, что это редкий пограничный кейс защиты от бесконечных циклов, а не баг повседневной логики.

> [!danger] **Когда стоит помнить об этом нюансе:**
>
> Если вы пишете сложную валидацию или автокоррекцию полей ввода, где эффект следит за `computed`-флагом ошибки и при его срабатывании тут же принудительно перезаписывает исходный `signal` в том же тике. В таком случае запись лучше обернуть в микротаск (`queueMicrotask`) или выполнять её в обработчике события до обновления сигнала.

### Что выбрать под конкретную задачу

> [!warning] Эта часть статьи на редактировании
>
> 1. Довести примеры до конца
> 2. Дописать ключевые отличия подходов

Современная фронтенд-разработка ушла от поиска «единственно верного» стейт-менеджера. Сравнение **@pravosleva/reactive-engine**, **Effector** и **Reatom** показывает, что все три решения способны закрывать задачи крупного продакшена, но делают это через разные архитектурные парадигмы:

* **Effector** — выбор для команд, которым ближе строгий функциональный стиль без классов. Его декларативные операторы (`sample`, `combine`) позволяют выстраивать предсказуемые потоки данных и строго контролировать зависимости в больших проектах.
* **Reatom (v1000+)** — мощный атомарный фреймворк с неявным контекстом выполнения и глубоким трекингом причинности, который отлично подходит для приложений со сложной композицией асинхронных цепочек и богатой экосистемой готовых расширений.
* **@pravosleva/reactive-engine (v3.0.0)** — полноценный промышленный стейт-менеджер для проектов любого масштаба, объединяющий экстремальную скорость интрузивного графа (`NodeLink` и `LinkPool`) с модульной сервисной архитектурой. Встроенный DI-контейнер (`provide` / `inject`), транзакционный батчинг, контроль гонок запросов и транзакционный логгер позволяют безопасно масштабировать кодовую базу в больших командах, сохраняя при этом рекордную компактность (~7.31 КБ Gzip) и переносимость логики между React, Vue и Angular.

В итоге выбор сводится не к размеру проекта, а к предпочтительной архитектуре вашей команды: **функциональные потоки событий (Effector)**, **атомарная композиция с трекингом контекста (Reatom)** или **высокоскоростной сигнальный граф с DI, сервисами и полным набором инструментов из коробки (@pravosleva/reactive-engine)**.

Ниже приведено решение одной и той же задачи на чистом JavaScript (ES2025+) с использованием актуальных версий инструментов: `@pravosleva/reactive-engine` v3.0.0, `@reatom/core` v1000+ и `effector` v23+.

Во всех трёх примерах реализованы:
- Два реактивных источника (`search` и `page`).
- Автоматический перезапуск GET-запроса с подстановкой значений в `URLSearchParams`.
- Подавление гонок Race Conditions через отмену предыдущего активного запроса (`AbortController`).
- Кастомная валидация ответа сервера перед сохранением результата.

1. `@pravosleva/reactive-engine` (v3.0.0)

Используем встроенный декларативный примитив `resource`, который сам управляет `AbortSignal`, реактивно отслеживает зависимости внутри `source` и поддерживает декларативную проверку ответа через `responseValidate`.

```ts
import { ReactiveEngine } from '@pravosleva/reactive-engine'
// ИЛИ можно юзать глобальный инстанс движка для небольших задач: import { signal, resource, effect } from '@pravosleva/reactive-engine'

const engine = new ReactiveEngine()

// 1. Создаём два сигнала
const search = engine.signal('reactive', 'search')
const page = engine.signal(1, 'page')

// 2. Объединяем параметры в вычисляемый источник
const queryParams = engine.computed(() => ({
  q: search.value.trim(),
  page: page.value,
}), 'queryParams')

// 3. Создаём ресурс с автоотменой (signal) и кастомной валидацией
const usersResource = engine.resource(
  async ({ q, page }, abortSignal) => {
    const params = new URLSearchParams({ q, page: String(page) })
    const res = await fetch(`https://example.com${!!params ? `?${params}` : ''}`, {
      signal: abortSignal,
    })

    if (!res.ok) {
      throw new Error(`HTTP error: ${res.status}`)
    }

    return res.json()
  },
  queryParams,
  {
    name: 'usersResource',
    validateBeforeFetch: ({ q }) => q.length >= 2 || 'Минимум 2 символа для поиска',
    responseValidate: (data) => {
      if (!data || !Array.isArray(data.items)) {
        return 'Некорректный формат ответа: ожидался массив items'
      }
      return true
    },
  }
)

// 4. Подписываемся на состояние ресурса
engine.effect(() => {
  const { loading, data, error } = usersResource.value
  console.log({ loading, data, error })
})

// Изменение сигналов мгновенно отменит первый запрос и запустит новый
search.value = 'signals'
page.value = 2
```

2. `effector` (v23+)

В Effector строится статическая топология потоков: объединяем сторы через `combine`, запускаем `createEffect` с ручным управлением `AbortController` для отмены предыдущего запроса и обрабатываем результат/ошибки через декларативные сторы.

```ts
import { createStore, createEvent, createEffect, combine, sample } from 'effector'

// 1. События и сторы-сигналы
const setSearch = createEvent()
const setPage = createEvent()

const $search = createStore('reactive').on(setSearch, (_, val) => val)
const $page = createStore(1).on(setPage, (_, val) => val)

// 2. Объединяем параметры в производный стор
const $query = combine({ search: $search, page: $page }, ({ search, page }) => ({
  q: search.trim(),
  page,
}))

// 3. Эффект с отменой предыдущего запроса через замыкание на активный AbortController
let activeController = null

const fetchUsersFx = createEffect(async ({ q, page }) => {
  if (activeController) {
    activeController.abort()
  }
  activeController = new AbortController()
  const { signal } = activeController

  const params = new URLSearchParams({ q, page: String(page) })
  const res = await fetch(`https://example.com${!!params ? `?${params}` : ''}`, { signal })

  if (!res.ok) {
    throw new Error(`HTTP error: ${res.status}`)
  }

  const data = await res.json()

  // Кастомная валидация ответа
  if (!data || !Array.isArray(data.items)) {
    throw new Error('Некорректный формат ответа: ожидался массив items')
  }

  return data
})

// 4. Сторы состояния и связывание потоков через sample
const $data = createStore(null).on(fetchUsersFx.doneData, (_, payload) => payload)
const $error = createStore(null)
  .on(fetchUsersFx.failData, (_, err) => (err.name === 'AbortError' ? null : err.message))
  .reset(fetchUsersFx)

const $state = combine({
  loading: fetchUsersFx.pending,
  data: $data,
  error: $error,
})

sample({
  clock: $query,
  filter: ({ q }) => q.length >= 2,
  target: fetchUsersFx,
})

// Первый запуск и подписка
$state.watch((s) => console.log(s))
fetchUsersFx($query.getState())

// Изменение сторов отменит предыдущий запрос и запустит новый
setSearch('signals')
setPage(2)
```

3. `@reatom/core` (v1000+)

В современной ветке Reatom (без явного `ctx`) используем атомы `atom`, вычисляемый поток с `withAsyncData` (или `effect` с `wrap`) и встроенный в контекст фрейма `AbortController` (`top().controller`), который автоматически абортируется при перезапуске вычисления.

```ts
import { atom, computed, effect, wrap, abortVar } from '@reatom/core'

// 1. Создаём два атома-сигнала
const search = atom('reactive', 'search')
const page = atom(1, 'page')

// 2. Вспомогательная функция валидации
function validateUsersPayload(data) {
  if (!data || !Array.isArray(data.items)) {
    throw new Error('Некорректный формат ответа: ожидался массив items')
  }
  return data
}

// 3. Реактивный эффект с автоматической отменой предыдущего фрейма
const state = atom({ loading: false, data: null, error: null }, 'usersState')

effect(async () => {
  const q = search().trim()
  const currentPage = page()

  if (q.length < 2) {
    state.set({ loading: false, data: null, error: 'Минимум 2 символа' })
    return
  }

  // Получаем AbortController текущего реактивного запуска
  const controller = abortVar.get()
  state.set((prev) => ({ ...prev, loading: true, error: null }))

  try {
    const params = new URLSearchParams({ q, page: String(currentPage) })
    const res = await wrap(
      fetch(`https://example.com${!!params ? `?${params}` : ''}`, {
        signal: controller?.signal,
      })
    )

    if (!res.ok) {
      throw new Error(`HTTP error: ${res.status}`)
    }

    const rawData = await wrap(res.json())
    const validData = validateUsersPayload(rawData)

    state.set({ loading: false, data: validData, error: null })
  } catch (err) {
    // Игнорируем ошибку отмены устаревшего запроса
    if (err?.name === 'AbortError') return
    state.set({ loading: false, data: null, error: err.message })
  }
}, 'fetchUsersEffect')

// 4. Подписываемся на итоговое состояние
effect(() => {
  console.log(state())
})

// Изменение атомов автоматически абортирует предыдущий fetch через abortVar
search.set('signals')
page.set(2)
```

**Ключевые отличия подходов**

- `@pravosleva/reactive-engine` v3.0.0: Декларативный resource берёт на себя и `AbortController`, и валидацию до/после запроса (`validateBeforeFetch` / `responseValidate`), и батчинг зависимостей (`computed`).
- `effector` v23+: Требует явного связывания потоков через `combine` и `sample`, а также ручного хранения ссылки на текущий `AbortController` внутри обработчика `createEffect`.
- `@reatom/core` v1000+: Использует встроенный механизм отмены асинхронного фрейма (`abortVar` + `wrap`), автоматически прерывая цепочку `await` при изменении любого атома, прочитанного до первого `await`.
